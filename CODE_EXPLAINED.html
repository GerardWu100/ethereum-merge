The Merge pipeline: reading the code

What this project computes, how the eight steps fit together, which settings matter, and where the sharp edges are.

How to use this

Sections follow execution order, which is also file order. Every code snippet is copied from the file named above it. Every number in a grey Sample data box was printed by running uv run ethereum-merge --smoke on the parquet files bundled in data/processed/; nothing here is estimated. Coloured boxes flag modelling choices and traps.

The process in plain English

Ethereum switched from proof of work to proof of stake on 15 September 2022, an event known as the Merge. The project asks a measurable question about it: does the futures basis - the gap between the futures price and the spot price - help predict how volatile the next 24 hours will be, and did that relationship change for Ethereum after the Merge in a way it did not change for Bitcoin?

To answer it the code loads one-minute spot prices and hourly quarterly futures for both coins, stitches the quarterly contracts into one continuous price series, computes the basis and the volatility of the following 24 hours at every hour, and then runs a difference-in-differences regression with Bitcoin as the control group. Three side analyses follow: a structural break test on the basis, a machine-learning exercise that scores which feature groups carry signal, and a chart that inspects whether the two coins moved in parallel before the Merge.

01How a run happens — cli.py, pipeline.py, config.py

The project is a notebook that was cut into eight numbered files. It is not a library of importable functions: it is a script that runs top to bottom, split across files. The three files in src/ethereum_merge/ exist only to make that run happen.

def run_pipeline(context_overrides: dict[str, Any] | None = None) -> dict[str, Any]:
    """Run each generated step script with a shared notebook-style context.

    Returns the final execution namespace so callers can inspect variables
    produced by the last step (for example with ``--print-keys``).
    """
    config = ProjectConfig()
    context = build_execution_context(
        config=config, context_overrides=context_overrides
    )

    # Step filenames are numbered so lexical sort preserves notebook order.
    for step_path in sorted(config.steps_dir.glob("*.py")):
        context["__file__"] = str(step_path)
        source = step_path.read_text()
        exec(compile(source, str(step_path), "exec"), context)

    return context
In plain words

run_pipeline reads the eight step files in numbered order and runs each one inside the same shared bag of variables, so a variable created in step 02 is still there in step 07 — exactly like cells in a notebook.

What it does

Input: an optional dictionary of overrides (the only one used in practice is the smoke-test window). Output: the final dictionary of every variable the eight steps created. Role: it is the whole program; cli.py and notebooks/demo.ipynb are one-line wrappers around it.

Why exec and not ordinary imports

The step files are not valid modules on their own: step 04 uses pd without importing it, and every step reads globals such as FIG_DIR that no step defines locally. Running them with exec into one dictionary reproduces notebook behaviour without rewriting the research code. The cost is that static tools cannot check the files, and your editor will mark most names as undefined.

Trap

Order comes from sorted(glob("*.py")), so it is lexical, not numeric. The two-digit prefixes (01_ to 08_) are what keep it correct. A ninth file named 9_extra.py would sort before 10_... but after 08_...; a file named 10_extra.py would sort before 9_extra.py. Keep the zero padding.

A file is named DA-16_ETH_USDT_..._hourly_2022-09_2022-12_binance_quarterly.parquet. Splitting on _hourly_ and taking the second underscore-separated token gives 2022-12, the expiry month. A missing spot file does not raise. It prints File not found and returns an empty frame, and the failure only surfaces several steps later as a confusing error inside the dollar-bar builder. Check the printed row counts at the top of any run.

04Step 03 — dollar bars

def build_dollar_bars(
    spot_df: pd.DataFrame,
    asset_label: str,
    quantile: float = 0.80,
) -> tuple[pd.DataFrame, float]:
    """Construct dollar bars for one asset using a turnover-quantile threshold."""
    tick_df = prepare_tick_frame(spot_df)

    # Threshold is a high-turnover minute proxy, not a fixed dollar amount.
    turnover = tick_df["price"] * tick_df["volume"]
    threshold = float(turnover.quantile(quantile))

    bars = dollar_bar_controller.handle_input_command(
        method_name="dollar_standard_bars",
        method_arguments={"threshold": threshold},
        input_data=tick_df,
    ).copy()
In plain words

Instead of one row per minute, make one row per fixed amount of money traded. Quiet hours produce few rows and busy hours produce many, so each row carries a similar amount of information.

What it does

Input: a minute-by-minute spot frame. Output: a bar frame and the dollar threshold used to build it. Role: feeds one figure and nothing else. No later step reads btc_dollar_bars or eth_dollar_bars.

The formula

Turnover in minute $t$ and the threshold:

$$D_t = P_t \, V_t, \qquad \theta = Q_{0.80}\big(\{D_t\}\big)$$

A new bar is closed as soon as the running sum of turnover since the last bar reaches $\theta$:

$$\sum_{u=\tau_{k-1}+1}^{\tau_k} D_u \;\ge\; \theta \;\Longrightarrow\; \text{bar } k \text{ closes at } \tau_k$$

$P_t$ is the closing price of minute $t$ in US dollars, $V_t$ is the coin volume traded in that minute, so $D_t$ is dollars traded. $Q_{0.80}$ is the 80th percentile: the level that 80 per cent of minutes fall below. $\tau_k$ is the minute at which bar $k$ closes.

ETH threshold 586,581.81 dollars, BTC threshold 767,112.89 dollars. From 64,800 minutes the builder produced 26,219 ETH bars and 25,949 BTC bars — roughly one bar every 2.5 minutes on average, but far denser around the Merge.

Why a percentile and not a round number

A fixed threshold such as one million dollars means something different for Bitcoin than for Ethereum, and something different in 2021 than in 2025. Taking the 80th percentile of one-minute turnover makes the threshold scale with the asset and the sample automatically.

The weakness, stated honestly

The threshold is computed from the whole sample, including the future. For a chart of sampling density that is harmless. It would not be acceptable if these bars fed a trading rule, because the bar boundaries in 2021 would depend on turnover observed in 2025. Since nothing downstream consumes the bars, this stays a presentational choice rather than a leak into the results.

05Step 04 — stitching quarterly futures into one series

Quarterly futures expire. To get one price history spanning years you must chain contracts together and remove the artificial jump that happens when you switch from one to the next. This step is the most intricate in the project, so it gets its own small diagram.

find_roll_point — when to switch contracts

def find_roll_point(current_data, next_data, expiry_date, roll_days=14):
    """Pick the roll timestamp in the overlap window closest to the ideal pre-expiry date."""
    overlap_times = set(current_data["datetime"]) & set(next_data["datetime"])
    if not overlap_times:
        return None

    ideal_roll = expiry_date - timedelta(days=roll_days)
    overlap_sorted = sorted(overlap_times)
    candidates = [timestamp for timestamp in overlap_sorted if timestamp <= ideal_roll]
    return max(candidates) if candidates else min(overlap_sorted)
In plain words

Switch to the next contract about two weeks before the current one expires, but only at a moment when both contracts are actually quoted. If there is no such moment that early, switch at the first moment both are quoted.

What it does

Input: the two contracts' frames, the current contract's expiry date, and the number of days before expiry to aim for. Output: one timestamp, or None when the two contracts never trade at the same hour. Role: defines where each segment is cut.

Trap

expiry_date is derived as pd.to_datetime(expiry + "-01") + MonthEnd(0), which gives 30 September 2022 at midnight. Binance quarterly contracts settle at 08:00 UTC on the last Friday of the month, which is 30 September 2022 for this contract. The derived date is right by luck here; for a quarter ending on a weekend it would be a day or two late. The roll is 14 days early, so the error never bites, but the constant is not what its name promises.

In plain words

Start from the newest contract and work backwards. At each switch, measure how much dearer the next contract is than the one being retired at the same instant, and shift the entire older history up by that amount so the chart has no artificial step.

What it does

Input: the stacked contracts frame. Output: one frame with columns datetime, raw_price, adjusted_price, adjustment, contract. Role: adjusted_price is plotted; raw_price is what step 05 uses to compute the basis.

The formula

Index the contracts $i = 1, \dots, n$ from oldest to newest, with roll time $\tau_i$ between contract $i$ and contract $i+1$. The newest contract is left alone, and each older one is shifted by the gap measured at its own roll:

$$a_n = 0, \qquad a_i = \tilde{P}^{\,i+1}(\tau_i) - P^{\,i}(\tau_i)$$

$$\tilde{P}^{\,i}(t) = P^{\,i}(t) + a_i$$

$P^{\,i}(t)$ is the raw closing price of contract $i$ at hour $t$, in US dollars. $\tilde{P}^{\,i}(t)$ is its adjusted price. $a_i$ is the adjustment in dollars, and because $\tilde{P}^{\,i+1}$ already contains $a_{i+1}$, the shifts accumulate as you walk back through history. This is the standard additive, or "Panama", roll adjustment. Returns computed within one segment are unchanged by $a_i$, since a constant cancels in a difference.

Why the last block drops overlapping timestamps

Both contracts are quoted during the overlap, so a naive concatenation would give two rows for the same hour. The final loop keeps only rows strictly later than the previous segment's last timestamp, which guarantees exactly one active contract per hour. Without it, the merge in step 05 would duplicate rows and quietly double-count observations in the regression.

Trap that was fixed here

The original code read the next contract's price from the first bar after the roll, not at the roll. For this ETH roll that meant $1346.69 - 1323.60 = 23.09$ instead of $5.26$: the December contract's one-hour move of 17.83 dollars was baked into the adjustment and then applied to every earlier hour in the series. See Fixes applied.

06Step 05 — basis and forward realized volatility

This is the step that creates the two quantities the study is about.

def calculate_rolling_rv_vectorized(hf_data, target_timestamps, window_hours=24):
    """Compute forward annualized realized volatility aligned to hourly targets."""
    # Resample to a strict 1-minute grid so rolling windows count minutes, not rows.
    df = hf_data[~hf_data.index.duplicated(keep="last")].copy()
    resampled_close = df["close"].resample("1min").ffill()

    log_return = np.log(resampled_close / resampled_close.shift(1))
    squared_returns = log_return**2

    minutes = window_hours * 60
    rolling_variance = squared_returns.rolling(window=minutes).sum()
    forward_variance = rolling_variance.shift(-minutes)

    annualization_factor = np.sqrt(525600 / minutes)
    forward_realized_vol = np.sqrt(forward_variance) * annualization_factor

    aligned_rv = forward_realized_vol.reindex(
        target_timestamps,
        method="nearest",
        tolerance=pd.Timedelta("5min"),
    )
    return aligned_rv.values
In plain words

At every hour, look forward over the next 24 hours of minute prices, add up the squared moves, take the square root, and scale it to a yearly number so it can be read like an option volatility.

What it does

Input: a minute-indexed spot frame and the list of hourly timestamps to report on. Output: a plain numpy array, one number per requested timestamp, aligned by position. Role: it produces the dependent variable of the regression, forward_vol_24h.

The formula

The one-minute log return, the forward realized variance over $h$ minutes, and its annualized form:

$$r_u = \ln\!\left(\frac{P_u}{P_{u-1}}\right), \qquad RV_{t,h} = \sum_{u=t+1}^{t+h} r_u^{2}, \qquad \sigma_{t,h} = \sqrt{RV_{t,h}} \times \sqrt{\frac{525600}{h}}$$

$P_u$ is the spot price at minute $u$ in US dollars. $r_u$ is its log return, a pure number. $h$ is the window length in minutes: 1,440 for 24 hours, 10,080 for 168 hours. $RV_{t,h}$ is the realized variance over the window that starts at $t$. The constant 525,600 is the number of minutes in a 365-day year, so $\sqrt{525600/h}$ converts a window figure into an annual one; for $h = 1440$ it equals 19.1050. $\sigma_{t,h}$ is therefore an annualized volatility, where 1.00 means 100 per cent a year.

The formula — basis

$$b_t = \frac{F_t - S_t}{S_t}$$

$F_t$ is the raw quarterly futures price at hour $t$ (raw_price), $S_t$ is the spot price at the same hour (spot_price), both in US dollars. $b_t$ is a fraction: positive means futures trade above spot, which is called contango; negative means below, which is called backwardation.

Why the outcome looks forward and the predictor does not

At hour $t$ the regression uses the basis observed at $t$ to explain volatility realized after $t$. That direction is deliberate: the question is whether the basis predicts volatility. It is the opposite of look-ahead bias, where a future value is used to explain the present.

Trap

resample("1min").ffill() carries the last price forward across gaps in the data. Every filled minute contributes a zero return, so a data outage looks like perfect calm and pulls the volatility estimate down. Nothing in the code counts how many minutes were filled.

The weakness, stated honestly

The 24-hour forward window straddles the Merge for observations in the last day before it. Those rows carry PostMerge = 0 but an outcome measured mostly after the event. The same applies over seven days for forward_vol_168h. A cleaner design would drop a window's worth of observations on each side of the event date.

07Step 06 — structural breaks and the DiD regression

compute_bsadf_path — testing for a regime change in the basis

def compute_bsadf_path(
    log_series: pd.Series, min_window: int = 120, step: int = 5
) -> pd.Series:
    """Compute BSADF statistics on an expanding window grid."""
    stats = []
    timestamps = []

    for end in range(min_window, len(log_series) + 1, step):
        window_series = log_series.iloc[:end]
        result = get_bsadf_statistic(
            log_price=window_series,
            min_sample_length=min_window,
            constant="ct",
            lags=1,
        )
        stats.append(result["bsadf"])
        timestamps.append(window_series.index[-1])

    return pd.Series(stats, index=pd.DatetimeIndex(timestamps), name="bsadf")
In plain words

Walk through the daily basis history one step at a time and, at each point, ask how strongly the series looks like it has stopped being stable and started trending explosively.

What it does

Input: a daily series of $\ln(1 + b_t)$. Output: a series of test statistics, one every step days. Role: it draws the structural-break figure. Its output does not enter the regression or any table.

The formula

The augmented Dickey-Fuller regression fitted on a window running from $r_1$ to $r_2$, with a constant and a time trend (that is what constant="ct" selects) and one lag:

$$\Delta y_u = \alpha + \beta u + \gamma\, y_{u-1} + \delta\, \Delta y_{u-1} + \varepsilon_u$$

$$ADF_{r_1, r_2} = \frac{\hat{\gamma}}{\mathrm{se}(\hat{\gamma})}, \qquad \mathrm{BSADF}_{r_2} = \max_{\,r_1 \,\in\, [0,\; r_2 - r_0]} ADF_{r_1, r_2}$$

$y_u = \ln(1 + b_u)$ is the log of one plus the daily average basis. $\Delta$ is the one-day change. $\gamma$ measures pull back towards the past level: a $\gamma$ near zero or above means no pull, which is the explosive case. $\hat{\gamma}$ is its estimate and $\mathrm{se}(\hat{\gamma})$ its standard error, so the ratio is an ordinary t-statistic. $r_0$ is the minimum window length, min_sample_length. BSADF stands for backward supremum ADF: at each end point $r_2$ it takes the largest statistic over all admissible start points. Because the maximum is taken over many overlapping regressions, the usual Dickey-Fuller critical values do not apply, which is why the code uses an empirical reference line instead.

On the full four-year sample the daily series is roughly 1,550 points, so the loop runs about 275 times over ever-longer windows. This is the slowest part of a full run by a wide margin.

The difference-in-differences regression

# Difference-in-differences model: triple interaction captures merge-specific basis effect.
formula = (
    "forward_vol_24h ~ basis + PostMerge + Ethereum + "
    "basis:PostMerge + basis:Ethereum + PostMerge:Ethereum + "
    "basis:PostMerge:Ethereum"
)

print("Running DiD Regression...")
model = smf.ols(formula=formula, data=pooled_data_clean).fit(
    cov_type="HAC", cov_kwds={"maxlags": 24}
)
In plain words

Fit one line through both coins at once, with switches for "is this Ethereum" and "is this after the Merge". The coefficient on all three terms multiplied together answers the actual research question.

The formula

$$ \sigma_{t,24h} = \beta_0 + \beta_1 b_t + \beta_2 D_t + \beta_3 E_t + \beta_4 b_t D_t + \beta_5 b_t E_t + \beta_6 D_t E_t + \beta_7 b_t D_t E_t + \varepsilon_t $$

$\sigma_{t,24h}$ is the annualized volatility of the next 24 hours. $b_t$ is the basis. $D_t$ is PostMerge, equal to 1 from 15 September 2022 onwards and 0 before. $E_t$ is Ethereum, equal to 1 for ETH rows and 0 for BTC rows. The one that matters is $\beta_7$: it is the change, after the Merge, in how strongly the basis maps into future volatility for Ethereum, over and above whatever changed for Bitcoin at the same time. HAC means heteroskedasticity and autocorrelation consistent standard errors; with maxlags = 24 the estimator allows each hour's error to be correlated with the previous 24 hours' errors, which is needed because consecutive 24-hour forward windows overlap.

The weakness, stated honestly

Both coins are pooled into one regression with no clustering by asset, so the standard errors treat a BTC hour and an ETH hour at the same moment as independent draws. Crypto returns are highly correlated across coins, so the true standard errors are wider than those printed and the stars overstate the confidence.

08Step 07 — meta-labelling and clustered feature importance

Two ideas from Marcos Lopez de Prado's Advances in Financial Machine Learning are applied here. Meta-labelling means: first decide the direction of a trade by a simple rule, then train a model whose only job is to say whether that trade would have worked. Clustered feature importance means: score groups of correlated features together rather than one at a time.

In plain words

Find the hours where the basis moved sharply, decide a long or short position from whether the basis is unusually high or low, follow each position until it gains enough, loses enough, or three days pass, and record whether it ended in profit. Then train a forest to see whether the features can tell the winners from the losers.

What it does

Input: one asset's merged frame plus the pooled feature table. Output: a frame indexed by event time with a 0 or 1 Label and the seven feature columns. Role: feeds the random forest, the importance table, the correlation heat map and the confusion matrix.

The formula — the event filter

The symmetric CUSUM (cumulative sum) filter keeps two running totals and fires when either crosses a threshold:

$$S^{+}_t = \max\big(0,\; S^{+}_{t-1} + \Delta b_t\big), \qquad S^{-}_t = \min\big(0,\; S^{-}_{t-1} + \Delta b_t\big)$$

$$\text{event at } t \iff S^{+}_t \ge h \;\text{ or }\; S^{-}_t \le -h, \qquad h = 0.5\,\mathrm{sd}(b)$$

$\Delta b_t = b_t - b_{t-1}$ is the hourly change in the basis. $S^{+}$ accumulates upward drift and resets to zero whenever it would go negative; $S^{-}$ does the mirror image. $h$ is the trigger level, here half the standard deviation of the basis over the sample. After each event both totals reset to zero, so the filter fires on sustained moves rather than on noise.

The formula — the triple barrier

For an event at time $t_0$ with position side $s \in \{-1, +1\}$ and barrier width driven by volatility $\sigma_{t_0}$:

$$\text{profit barrier} = 1.5\,\sigma_{t_0}, \qquad \text{loss barrier} = -1.5\,\sigma_{t_0}, \qquad \text{time barrier} = t_0 + 3\ \text{days}$$

$$R = s \times \left(\frac{P_{t_1}}{P_{t_0}} - 1\right), \qquad \text{Label} = \mathbf{1}\{R > 0\}$$

$P_{t_0}$ is the futures price when the event fires and $P_{t_1}$ the price when the first of the three barriers is touched. $s$ is $+1$ when the basis is in its top fifth and $-1$ when it is in its bottom fifth. $\sigma_{t_0}$ is an exponentially weighted standard deviation of hourly log returns with span 48, so barriers are wide in turbulent periods and narrow in calm ones. $\mathbf{1}\{\cdot\}$ is 1 when the condition holds and 0 otherwise, so the label answers "would this position have made money", not "which way did the price go".

The formula — clustered importance

$$L = -\frac{1}{N}\sum_{j=1}^{N}\Big[y_j \ln \hat{p}_j + (1-y_j)\ln(1-\hat{p}_j)\Big], \qquad I_k = L^{(k)} - L^{(0)}$$

$L$ is log loss: $N$ is the number of events, $y_j$ the true label of event $j$, $\hat p_j$ the probability the forest assigns to label 1. $L^{(0)}$ is the loss on the untouched data and $L^{(k)}$ the loss after the rows of cluster $k$ have been shuffled together. A large positive $I_k$ means breaking that cluster hurt the model, so the cluster carried information. Shuffling the cluster's columns as one block, rather than column by column, is the point: correlated features cannot cover for each other.

The weakness, stated honestly

Both the accuracy and the importances are in-sample: model.fit and model.predict_proba see the same 57 rows. The published version of this method computes importance out of sample across cross-validation folds, with purging and embargoing to stop overlapping label windows leaking between folds. As written, the 0.88 accuracy says the forest can memorise 57 rows, which it can.

Second weakness

The features are the same seven columns the regression uses, and three of them (PostMerge, Ethereum, PostMerge_Ethereum) are constants or near-constants within an asset and period. A forest can separate the four groups perfectly from those alone, which is part of why the importances are not small.

In plain words

Average the volatility to daily numbers, set both coins to 100 at the start of the window, and draw them so a reader can judge by eye whether they moved together before the Merge.

What it does

Input: the two merged frames, the Merge date, and a window of 90 days on each side. Output: one figure, 03_causal_parallel_trends.png. Role: it is the visual check of the assumption the difference-in-differences design rests on — that without the Merge, ETH and BTC volatility would have carried on moving in parallel.

Trap

Both series are divided by their own first value, .iloc[0]. That single day sets the level of both lines for the whole chart. A quiet first day makes both lines look like they exploded; a turbulent one flattens everything. Changing window_days changes the base day and therefore the whole picture, without changing any underlying data.

The weakness, stated honestly

Nothing tests the parallel-trends assumption formally. There is no pre-Merge placebo regression and no event-study plot of period-by-period differences. The chart invites the reader to judge, and a reader who wants the assumption to hold will usually decide that it does.

15Traps and gotchas

The trapWhy it bites
One namespace for eight filesAny step can overwrite any earlier step's variable, and nothing warns. The eth_threshold collision fixed above is one instance; the pattern remains available to the next person who adds a step.
Automatic unused-import removal breaks the pipelineStep 01 imports numpy, pandas, matplotlib and seaborn for the benefit of later files, so within its own file they look unused. 16Limitations, stated honestly

  • Every number on this page comes from the smoke window, 1 September to 15 October 2022. A full run over 2021-06 to 2025-08 was not performed here: the structural break loop alone would refit the test a few hundred times over windows up to 1,500 days long. The smoke run finishes in about 23 seconds; a full run is a different order of magnitude and was out of scope for documenting the code.
  • The DiD table is not a finding. Six weeks of hourly data around one event, two assets, no clustered standard errors and no placebo test. The code is verified; the economics is not.
  • Bitcoin as a control group is an assumption, not a fact. The design needs BTC volatility to be what ETH volatility would have done without the Merge. Step 08 draws a picture of that assumption; nothing tests it.
  • The pipeline has one test. tests/test_smoke_pipeline.py checks that a smoke run finishes and returns a dictionary. No function has a unit test, so a wrong number is only caught by reading the output.
  • Most tunable values are not in config.toml. Changing the roll days, the barrier widths, or the break-test window means editing source files.
  • The dependency on RiskLabAI is a moving target. It is installed from a Git branch, not a release. The pin had already gone stale once; it can again.

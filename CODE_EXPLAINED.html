The Merge pipeline: reading the code

What the project computes, how its eight steps connect, which settings matter, and where it can fail.

How to use this

Sections follow execution order and file order. Each code snippet is copied from the file named above it. Every number in a grey Sample data box came from uv run ethereum-merge --smoke run on Parquet files, a column-oriented data format, in data/processed/; no number is estimated. Coloured boxes mark modelling choices and traps.

The process in plain English

Ethereum switched from proof of work to proof of stake on 15 September 2022. This event is called the Merge. The project asks whether the futures basis—the gap between the futures price and the spot price—helps predict volatility over the next 24 hours. It also asks whether that relationship changed for Ethereum after the Merge but not for Bitcoin.

The code loads one-minute spot prices and hourly quarterly futures for both coins, joins the quarterly contracts into one continuous price series, computes the basis and next-24-hour volatility, and runs a difference-in-differences regression, which compares before-and-after changes across groups, with Bitcoin as the control group, the comparison group. Three side analyses test for a structural break—a change in a series' behaviour—in the basis, measure which feature groups help a machine-learning model that learns patterns from data, and show whether the two coins moved in parallel before the Merge.

01How a run works — cli.py, pipeline.py, config.py

The project started as a notebook and is now split across eight numbered files. It is a script that runs from top to bottom, not a library of importable functions. The three files in src/ethereum_merge/ support that run.

def run_pipeline(context_overrides: dict[str, Any] | None = None) -> dict[str, Any]:
    """Run each generated step script with a shared notebook-style context.

    Returns the final execution namespace so callers can inspect variables
    produced by the last step (for example with ``--print-keys``).
    """
    config = ProjectConfig()
    context = build_execution_context(
        config=config, context_overrides=context_overrides
    )

    # Step filenames are numbered so lexical sort preserves notebook order.
    for step_path in sorted(config.steps_dir.glob("*.py")):
        context["__file__"] = str(step_path)
        source = step_path.read_text()
        exec(compile(source, str(step_path), "exec"), context)

    return context
In plain words

run_pipeline reads the eight step files in numbered order and runs them in one shared set of variables. A variable created in step 02 is still available in step 07, as it would be in a notebook.

What it does

Input: an optional dictionary of overrides. In practice, it supplies the smoke-test window. Output: the final dictionary of variables created by the eight steps. Role: it is the whole program; cli.py and notebooks/demo.ipynb call it.

The returned dictionary holds 118 names that do not start with an underscore. Imported modules share the dictionary with the data frames because exec puts every name a step creates, including imports, into the same namespace.

Why exec and not ordinary imports

The step files are not valid modules on their own. Step 04 uses pd without importing it, and every step reads global names such as FIG_DIR that no step defines locally. Running them with exec in one dictionary preserves the notebook behaviour without rewriting the research code. The cost is that static tools cannot check the files and editors mark many names as undefined.

Trap

Order comes from sorted(glob("*.py")), so it is lexical, not numeric. The two-digit prefixes (01_ to 08_) make that order correct. A ninth file named 9_extra.py would sort before 10_... but after 08_...; a file named 10_extra.py would sort before 9_extra.py. Keep the leading zero.

04Step 03 — dollar bars

def build_dollar_bars(
    spot_df: pd.DataFrame,
    asset_label: str,
    quantile: float = 0.80,
) -> tuple[pd.DataFrame, float]:
    """Construct dollar bars for one asset using a turnover-quantile threshold."""
    tick_df = prepare_tick_frame(spot_df)

    # Threshold is a high-turnover minute proxy, not a fixed dollar amount.
    turnover = tick_df["price"] * tick_df["volume"]
    threshold = float(turnover.quantile(quantile))

    bars = dollar_bar_controller.handle_input_command(
        method_name="dollar_standard_bars",
        method_arguments={"threshold": threshold},
        input_data=tick_df,
    ).copy()
In plain words

A dollar bar groups trades until a fixed dollar value has changed hands, rather than grouping one row per minute. Quiet periods produce fewer rows and busy periods produce more.

What it does

Input: a minute-by-minute spot frame. Output: a bar frame and the dollar threshold used to build it. Role: feeds one figure only. No later step reads btc_dollar_bars or eth_dollar_bars.

The formula

Dollar turnover in minute $t$ and the threshold:

$$D_t = P_t \, V_t, \qquad \theta = Q_{0.80}\big(\{D_t\}\big)$$

The code closes a bar when turnover since the previous bar reaches $\theta$:

$$\sum_{u=\tau_{k-1}+1}^{\tau_k} D_u \;\ge\; \theta \;\Longrightarrow\; \text{bar } k \text{ closes at } \tau_k$$

$P_t$ is the closing price of minute $t$ in US dollars. $V_t$ is the coin volume traded in that minute, so $D_t$ is dollars traded. $Q_{0.80}$ is the 80th percentile: 80 per cent of minutes have lower turnover. $\tau_k$ is the minute when bar $k$ closes.

The ETH threshold is 586,581.81 dollars and the BTC threshold is 767,112.89 dollars. From 64,800 minutes, the builder produced 26,219 ETH bars and 25,949 BTC bars—about one bar every 2.5 minutes on average, with more bars around the Merge.

Why a percentile and not a round number

A fixed threshold such as one million dollars means different things for Bitcoin and Ethereum, and in 2021 and 2025. Taking the 80th percentile of one-minute turnover scales the threshold to the asset and sample.

The weakness, stated honestly

The threshold uses the whole sample, including future data. That is harmless for a sampling-density chart. It would be invalid for a trading rule because 2021 bar boundaries would depend on turnover from 2025. Since later steps do not use the bars, this does not leak into the results.

05Step 04 — joining quarterly futures into one series

Quarterly futures contracts expire. To build one multi-year price history, the code joins the contracts and removes the artificial jump at each switch. This is the most involved step, so it has its own diagram.

find_roll_point — choose when to switch contracts

def find_roll_point(current_data, next_data, expiry_date, roll_days=14):
    """Pick the roll timestamp in the overlap window closest to the ideal pre-expiry date."""
    overlap_times = set(current_data["datetime"]) & set(next_data["datetime"])
    if not overlap_times:
        return None

    ideal_roll = expiry_date - timedelta(days=roll_days)
    overlap_sorted = sorted(overlap_times)
    candidates = [timestamp for timestamp in overlap_sorted if timestamp <= ideal_roll]
    return max(candidates) if candidates else min(overlap_sorted)
In plain words

Switch to the next contract about two weeks before expiry, but only when both contracts have a quote. If no such time exists by then, switch at the first time both have a quote.

What it does

Input: the two contract frames, the current expiry date, and the target number of days before expiry. Output: one timestamp, or None if the contracts never trade in the same hour. Role: chooses where each segment ends.

Trap

expiry_date is derived as pd.to_datetime(expiry + "-01") + MonthEnd(0), which gives 30 September 2022 at midnight. Binance quarterly contracts settle at 08:00 UTC on the last Friday of the month, also 30 September 2022 for this contract. The derived date is only right by chance; for a quarter ending on a weekend it would be a day or two late. The roll is 14 days early, so this does not affect the result here, but the variable name is misleading.

In plain words

Start with the newest contract and work backwards. At each switch, measure the price gap between the new and old contracts at the same instant. Add that gap to the entire older history.

What it does

Input: the stacked contracts frame. Output: one frame with columns datetime, raw_price, adjusted_price, adjustment, contract. Role: step 05 plots adjusted_price and uses raw_price to compute the basis.

The formula

Index the contracts $i = 1, \dots, n$ from oldest to newest, with roll time $\tau_i$ between contract $i$ and contract $i+1$. The newest contract stays unchanged. Each older contract is shifted by the gap at its roll:

$$a_n = 0, \qquad a_i = \tilde{P}^{\,i+1}(\tau_i) - P^{\,i}(\tau_i)$$

$$\tilde{P}^{\,i}(t) = P^{\,i}(t) + a_i$$

$P^{\,i}(t)$ is the raw closing price of contract $i$ at hour $t$, in US dollars. $\tilde{P}^{\,i}(t)$ is its adjusted price. $a_i$ is the dollar adjustment. Because $\tilde{P}^{\,i+1}$ already includes $a_{i+1}$, the adjustments accumulate as the code moves back through history. This is the standard additive, or "Panama", roll adjustment. Returns within one contract segment do not change by $a_i$ because the same constant is added to both prices.

Why the last block drops overlapping timestamps

Both contracts have quotes during the overlap, so simple concatenation would create two rows for one hour. The final loop keeps only rows strictly later than the previous segment's last timestamp. That leaves one active contract per hour. Without it, step 05 would duplicate rows and double-count observations in the regression.

Trap that was fixed here

The original code used the next contract's first bar after the roll, not its price at the roll. For this ETH roll, that gave $1346.69 - 1323.60 = 23.09$ instead of $5.26$. The December contract's one-hour move of 17.83 dollars was then added to every earlier hour. See Fixes applied.

06Step 05 — basis and next-period volatility

This step creates the two quantities used in the study.

def calculate_rolling_rv_vectorized(hf_data, target_timestamps, window_hours=24):
    """Compute forward annualized realized volatility aligned to hourly targets."""
    # Resample to a strict 1-minute grid so rolling windows count minutes, not rows.
    df = hf_data[~hf_data.index.duplicated(keep="last")].copy()
    resampled_close = df["close"].resample("1min").ffill()

    log_return = np.log(resampled_close / resampled_close.shift(1))
    squared_returns = log_return**2

    minutes = window_hours * 60
    rolling_variance = squared_returns.rolling(window=minutes).sum()
    forward_variance = rolling_variance.shift(-minutes)

    annualization_factor = np.sqrt(525600 / minutes)
    forward_realized_vol = np.sqrt(forward_variance) * annualization_factor

    aligned_rv = forward_realized_vol.reindex(
        target_timestamps,
        method="nearest",
        tolerance=pd.Timedelta("5min"),
    )
    return aligned_rv.values
In plain words

For each hour, look at the next 24 hours of minute prices, add the squared moves, take the square root, and scale the result to a yearly number.

What it does

Input: a spot frame indexed by minute and the hourly timestamps to report. Output: a plain numpy array, one number per requested timestamp, aligned by position. Role: it produces the regression's outcome, forward_vol_24h.

The formula

The one-minute log return, realized variance over $h$ future minutes, and annualized volatility:

$$r_u = \ln\!\left(\frac{P_u}{P_{u-1}}\right), \qquad RV_{t,h} = \sum_{u=t+1}^{t+h} r_u^{2}, \qquad \sigma_{t,h} = \sqrt{RV_{t,h}} \times \sqrt{\frac{525600}{h}}$$

$P_u$ is the spot price at minute $u$ in US dollars. $r_u$ is its log return, a pure number. $h$ is the window length in minutes: 1,440 for 24 hours, 10,080 for 168 hours. $RV_{t,h}$ is the realized variance in the window that starts at $t$. The constant 525,600 is the number of minutes in a 365-day year, so $\sqrt{525600/h}$ annualizes the window; for $h = 1440$ it equals 19.1050. $\sigma_{t,h}$ is annualized volatility, where 1.00 means 100 per cent a year.

The formula — basis

$$b_t = \frac{F_t - S_t}{S_t}$$

$F_t$ is the raw quarterly futures price at hour $t$ (raw_price), and $S_t$ is the spot price at the same hour (spot_price), both in US dollars. $b_t$ is a fraction. A positive value means futures trade above spot, called contango; a negative value means they trade below spot, called backwardation.

Why the outcome looks forward and the predictor does not

At hour $t$, the regression uses the basis observed at $t$ to explain volatility realized after $t$. That matches the prediction question. It avoids look-ahead bias, which uses a future value to explain the present.

Trap

resample("1min").ffill() carries the last price across data gaps. Each filled minute contributes a zero return, so an outage looks calm and lowers the volatility estimate. The code does not count filled minutes.

The weakness, stated honestly

The 24-hour forward window crosses the Merge for observations in the last day before it. Those rows have PostMerge = 0 but an outcome measured mostly after the event. The same issue lasts seven days for forward_vol_168h. A cleaner design would drop one window of observations on each side of the event.

07Step 06 — structural breaks and the difference-in-differences regression

compute_bsadf_path — test for a change in the basis

def compute_bsadf_path(
    log_series: pd.Series, min_window: int = 120, step: int = 5
) -> pd.Series:
    """Compute BSADF statistics on an expanding window grid."""
    stats = []
    timestamps = []

    for end in range(min_window, len(log_series) + 1, step):
        window_series = log_series.iloc[:end]
        result = get_bsadf_statistic(
            log_price=window_series,
            min_sample_length=min_window,
            constant="ct",
            lags=1,
        )
        stats.append(result["bsadf"])
        timestamps.append(window_series.index[-1])

    return pd.Series(stats, index=pd.DatetimeIndex(timestamps), name="bsadf")
In plain words

Move through the daily basis history and ask at each point whether the series has stopped being stable and started rising explosively.

What it does

Input: a daily series of $\ln(1 + b_t)$. Output: one test statistic every step days. Role: draws the structural-break figure. Its output does not enter the regression or a table.

The formula

The augmented Dickey-Fuller (ADF) regression fits a window from $r_1$ to $r_2$, with a constant, a time trend (selected by constant="ct"), and one lag:

$$\Delta y_u = \alpha + \beta u + \gamma\, y_{u-1} + \delta\, \Delta y_{u-1} + \varepsilon_u$$

$$ADF_{r_1, r_2} = \frac{\hat{\gamma}}{\mathrm{se}(\hat{\gamma})}, \qquad \mathrm{BSADF}_{r_2} = \max_{\,r_1 \,\in\, [0,\; r_2 - r_0]} ADF_{r_1, r_2}$$

$y_u = \ln(1 + b_u)$ is the log of one plus the daily average basis. $\Delta$ is the one-day change. $\gamma$ measures pull toward the past level: a $\gamma$ near zero or above means no pull, which is the explosive case. $\hat{\gamma}$ is its estimate and $\mathrm{se}(\hat{\gamma})$ its standard error, so their ratio is a t-statistic. $r_0$ is the minimum window length, min_sample_length. BSADF means backward supremum augmented Dickey-Fuller. At each end point $r_2$, it takes the largest statistic over all allowed start points. Because it maximizes across many overlapping regressions, ordinary Dickey-Fuller critical values do not apply; the code uses an empirical reference line.

The difference-in-differences regression

# Difference-in-differences model: triple interaction captures merge-specific basis effect.
formula = (
    "forward_vol_24h ~ basis + PostMerge + Ethereum + "
    "basis:PostMerge + basis:Ethereum + PostMerge:Ethereum + "
    "basis:PostMerge:Ethereum"
)

print("Running DiD Regression...")
model = smf.ols(formula=formula, data=pooled_data_clean).fit(
    cov_type="HAC", cov_kwds={"maxlags": 24}
)
In plain words

Fit both coins in one model, with indicators for Ethereum and the post-Merge period. The coefficient on the product of all three terms answers the research question.

The formula

$$ \sigma_{t,24h} = \beta_0 + \beta_1 b_t + \beta_2 D_t + \beta_3 E_t + \beta_4 b_t D_t + \beta_5 b_t E_t + \beta_6 D_t E_t + \beta_7 b_t D_t E_t + \varepsilon_t $$

$\sigma_{t,24h}$ is annualized volatility over the next 24 hours. $b_t$ is the basis. $D_t$ is PostMerge, equal to 1 from 15 September 2022 onward and 0 before. $E_t$ is Ethereum, equal to 1 for ETH rows and 0 for BTC rows. The key term is $\beta_7$: the post-Merge change in how strongly the basis maps to future Ethereum volatility, beyond any simultaneous change for Bitcoin. HAC means heteroskedasticity and autocorrelation consistent standard errors. With maxlags = 24, the estimator allows each hour's error to correlate with the previous 24 hours' errors because consecutive 24-hour forward windows overlap.

The weakness, stated honestly

Both coins are pooled in one regression without clustering by asset. The standard errors therefore treat BTC and ETH at the same moment as independent observations. Crypto returns are highly correlated, so the true standard errors are likely wider and the significance stars too strong.

08Step 07 — meta-labelling and grouped feature importance

This step uses two ideas from Marcos Lopez de Prado's Advances in Financial Machine Learning. Meta-labelling first chooses a trade direction with a simple rule, then trains a model to predict whether the trade would work. Grouped feature importance scores correlated features together instead of one at a time.

    # CUSUM filter finds basis shocks large enough to treat as tradeable events.
    cusum_threshold = basis_series.std() * 0.5
    raw_events = rl_labeling.symmetric_cusum_filter(
        basis_series, threshold=cusum_threshold
    )

    upper, lower = basis_series.quantile(0.80), basis_series.quantile(0.20)
    side_series = pd.Series(index=basis_series.index, dtype=float)
    side_series[basis_series >= upper] = 1.0
    side_series[basis_series <= lower] = -1.0
    side_series = side_series.dropna()

    event_index = raw_events.intersection(side_series.index)
    ...
    events = rl_labeling.meta_events(
        close=price_series,
        time_events=event_index,
        ptsl=[1.5, 1.5],
        target=ewm_vol,
        return_min=ewm_vol.quantile(0.3),
        vertical_barrier_times=vertical_times,
        side=side_series,
        num_threads=1,
    )
In plain words

Find hours when the basis moved sharply. Choose a long or short position from whether the basis is unusually high or low. Follow each position until it gains enough, loses enough, or three days pass, then record whether it made money. Finally, train a forest to see whether the features predict the winners.

What it does

Input: one asset's merged frame and the pooled feature table. Output: a frame indexed by event time with a 0 or 1 Label and seven feature columns. Role: feeds the random forest, importance table, correlation heat map, and confusion matrix.

The formula — the event filter

The symmetric CUSUM (cumulative sum) filter keeps an upward and a downward running total. It fires when either crosses a threshold:

$$S^{+}_t = \max\big(0,\; S^{+}_{t-1} + \Delta b_t\big), \qquad S^{-}_t = \min\big(0,\; S^{-}_{t-1} + \Delta b_t\big)$$

$$\text{event at } t \iff S^{+}_t \ge h \;\text{ or }\; S^{-}_t \le -h, \qquad h = 0.5\,\mathrm{sd}(b)$$

$\Delta b_t = b_t - b_{t-1}$ is the hourly basis change. $S^{+}$ accumulates upward movement and resets to zero if it would go negative; $S^{-}$ does the reverse. $h$ is the trigger level, here half the basis standard deviation over the sample. After each event, both totals reset to zero, so the filter responds to sustained moves rather than noise.

The formula — the triple barrier

For an event at time $t_0$, position side $s \in \{-1, +1\}$, and volatility $\sigma_{t_0}$:

$$\text{profit barrier} = 1.5\,\sigma_{t_0}, \qquad \text{loss barrier} = -1.5\,\sigma_{t_0}, \qquad \text{time barrier} = t_0 + 3\ \text{days}$$

$$R = s \times \left(\frac{P_{t_1}}{P_{t_0}} - 1\right), \qquad \text{Label} = \mathbf{1}\{R > 0\}$$

$P_{t_0}$ is the futures price when the event fires and $P_{t_1}$ the price when the first barrier is touched. $s$ is $+1$ when the basis is in its top fifth and $-1$ when it is in its bottom fifth. $\sigma_{t_0}$ is an exponentially weighted standard deviation of hourly log returns with span 48, so barriers are wider in turbulent periods and narrower in calm ones. $\mathbf{1}\{\cdot\}$ is 1 when the condition holds and 0 otherwise. The label therefore says whether the position made money, not which way the price moved.

The formula — clustered importance

$$L = -\frac{1}{N}\sum_{j=1}^{N}\Big[y_j \ln \hat{p}_j + (1-y_j)\ln(1-\hat{p}_j)\Big], \qquad I_k = L^{(k)} - L^{(0)}$$

$L$ is log loss: $N$ is the number of events, $y_j$ the true label of event $j$, and $\hat p_j$ the forest's probability for label 1. $L^{(0)}$ is the loss on untouched data; $L^{(k)}$ is the loss after shuffling cluster $k$'s rows together. A large positive $I_k$ means the shuffle harmed the model, so the cluster carried information. Shuffling a cluster as one block stops correlated features from covering for one another.

The weakness, stated honestly

Both the accuracy and the importance scores are in-sample: model.fit and model.predict_proba use the same 57 rows. The published method measures importance out of sample across cross-validation folds, with purging and embargoing to prevent overlapping label windows from leaking between folds. Here, 0.88 only shows that the forest can fit 57 rows.

Second weakness

The features are the same seven columns used by the regression. Three (PostMerge, Ethereum, PostMerge_Ethereum) are constant or nearly constant within an asset and period. Those alone can let a forest separate the four groups, which helps explain the importance scores.

In plain words

Average volatility by day, set both coins to 100 at the window start, and plot them so the reader can judge whether they moved together before the Merge.

What it does

Input: the two merged frames, the Merge date, and a 90-day window on each side. Output: one figure, 03_causal_parallel_trends.png. Role: it is the visual check of the assumption behind the difference-in-differences design: without the Merge, ETH and BTC volatility would have continued to move in parallel.

Trap

Each series is divided by its first value, .iloc[0]. That day sets the level for the whole chart. A quiet first day makes both lines look explosive; a turbulent one flattens them. Changing window_days changes the base day and the picture, not the underlying data.

The weakness, stated honestly

Nothing formally tests the parallel-trends assumption. There is no pre-Merge placebo regression or event-study plot of period-by-period differences. The chart asks the reader to judge, which makes the conclusion subjective.

16Limitations

  • Every number on this page comes from the smoke window, 1 September to 15 October 2022. A full run over 2021-06 to 2025-08 was not performed. The structural break loop alone would refit the test a few hundred times over windows up to 1,500 days. The smoke run takes about 23 seconds; a full run was outside the scope of this page.
  • The DiD table is not a finding. It uses six weeks of hourly data around one event and two assets, with no clustered standard errors or placebo test. The code is verified; the economic claim is not.
  • Bitcoin as a control group is an assumption, not a fact. The design assumes BTC volatility represents what ETH volatility would have done without the Merge. Step 08 shows this assumption; nothing tests it.
  • The pipeline has one test. tests/test_smoke_pipeline.py checks that a smoke run finishes and returns a dictionary. No function has a unit test, so a wrong number is caught only by reading the output.
  • Most tunable values are not in config.toml. Changing roll days, barrier widths, or the break-test window requires editing source files.
  • The RiskLabAI dependency can change. It is installed from a Git branch, not a release. Its pin has already gone stale once.
